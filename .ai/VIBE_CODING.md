# Vibe Coding Workflow

## Principle

한 번에 하나의 명확한 결과를 만든다. 빠르게 생성하는 것보다 작은 피드백 루프를
반복해 코드가 실제로 동작하는 상태를 유지하는 것이 중요하다.

## Loop

1. **Define** — 이번 단계의 사용자 가치와 완료 조건을 한 문장으로 정한다.
2. **Inspect** — 관련 코드, 문서, 테스트, 최근 변경을 확인한다.
3. **Plan** — 바꿀 파일과 검증 방법을 정한다.
4. **Implement** — 최소 변경으로 기능을 만든다.
5. **Verify** — 가장 가까운 테스트부터 실행한다.
6. **Review** — 범위 초과, 보안, 호환성, 복잡성을 점검한다.
7. **Report** — 결과, 검증, 남은 위험, 다음 선택지를 알린다.

## Feature Size

좋은 작업 단위는 독립적으로 설명하고 테스트하고 되돌릴 수 있다. 다음 항목이 한 작업에
섞이면 분리를 검토한다.

- 서로 다른 사용자 기능
- 스키마 마이그레이션과 대규모 리팩터링
- 의존성 업그레이드와 기능 개발
- 포맷 전면 변경과 버그 수정

## AI Rules

- 빈 저장소가 아니면 전체 앱을 새로 생성하기 전에 기존 구조를 읽는다.
- 사용자가 실제 파일 수정을 요청했다면 답변에 코드만 나열하지 말고 파일을 수정하고 검증한다.
- 실행 결과와 오류를 근거로 다음 단계를 정한다.
- 오류가 반복되면 같은 수정을 반복하지 말고 가설을 갱신한다.
- 기능이 검증되기 전 다음 기능으로 확장하지 않는다.

## Human Checkpoints

다음과 같은 중요한 선택에서 사용자의 확인을 구한다.

- 데이터 손실 가능성이 있는 마이그레이션
- 공개 API의 호환성 파괴
- 핵심 아키텍처 변경
- 유료 서비스 또는 새로운 외부 시스템 도입
- 권한·보안 모델 변경

사소하고 되돌릴 수 있는 구현 세부사항은 합리적으로 결정하고 근거를 보고한다.

## Commit Guidance

Git 작업을 요청받은 경우에만 커밋한다. 커밋은 하나의 논리적 변경을 담고, 메시지는
무엇을 했는지보다 왜 필요한지가 드러나게 작성한다. 관련 없는 사용자 변경을 포함하지 않는다.
