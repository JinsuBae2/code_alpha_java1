# Backend Rules

이 문서는 Java/Spring 계열 프로젝트에 적용한다. 정확한 버전과 도구는 빌드 파일,
래퍼, CI 설정, `PROJECT_RULES.md`에서 확인하며 임의로 고정하지 않는다.

## Architecture

- 저장소의 기존 아키텍처를 우선한다.
- Controller는 HTTP 경계 처리에 집중한다.
- 비즈니스 규칙은 기존 서비스 또는 도메인 계층에 둔다.
- 데이터 접근은 기존 Repository/DAO 패턴을 따른다.
- 단순 CRUD에 불필요한 인터페이스·Facade·Manager 계층을 추가하지 않는다.

## Dependency Injection

- 프로젝트가 사용하는 주입 방식을 따른다.
- 새 코드에서는 의존성이 명시되는 생성자 주입을 우선한다.
- 숨은 전역 상태와 서비스 로케이터를 피한다.

## DTO and Mapping

- 외부 요청·응답 계약을 영속성 엔티티와 분리하는 기존 방식을 따른다.
- Entity를 직접 API 응답으로 노출하지 않는다.
- 매핑 도구는 이미 사용 중일 때 재사용하며 작은 매핑을 위해 새 의존성을 추가하지 않는다.
- 업데이트 시 허용 필드와 누락 필드의 의미를 명확히 한다.

## Validation and Errors

- 형식 검증은 입력 경계에서, 비즈니스 규칙은 적절한 도메인/서비스 계층에서 처리한다.
- 일관된 오류 응답과 기존 전역 예외 처리 방식을 사용한다.
- 예외를 빈 `catch`로 삼키거나 정상 결과처럼 변환하지 않는다.
- 내부 예외 메시지와 스택 추적을 클라이언트에 노출하지 않는다.

## Persistence and Transactions

- 트랜잭션 경계를 명시적으로 이해하고 필요한 범위만 묶는다.
- 지연 로딩, N+1, 대량 조회, 잠금 영향을 점검한다.
- 스키마 변경은 요청 범위에 포함된 경우에만 수행하고 마이그레이션과 롤백을 제공한다.
- 운영 데이터 삭제 또는 변환은 별도 안전 검토 없이 자동 실행하지 않는다.

## Security

- 비밀번호는 검증된 단방향 비밀번호 해시를 사용한다.
- 인증 정보와 비밀값은 환경 또는 승인된 비밀 관리 시스템에서 읽는다.
- 엔드포인트마다 인증과 객체·행 수준 권한을 모두 검토한다.
- 로그에 토큰, 세션, 비밀번호, 개인정보를 남기지 않는다.

## Verification

가능한 범위에서 다음 순서로 확인한다.

1. 프로젝트가 지정한 포맷·정적 검사
2. 관련 단위 테스트
3. 통합 테스트
4. 전체 빌드
5. 데이터베이스 및 외부 연동이 필요한 흐름
