# API Rules

## Source of Truth

기존 OpenAPI 문서, API 명세, 계약 테스트, 라우팅 코드 순으로 실제 계약을 확인한다.
문서와 코드가 다르면 차이를 보고하고 임의로 한쪽을 정답으로 가정하지 않는다.

## Design

- 리소스와 행위가 명확한 기존 URL·명명 규칙을 따른다.
- HTTP 메서드와 상태 코드를 의미에 맞게 사용한다.
- 요청과 응답 스키마를 명시하고 선택·필수·nullable 필드를 구분한다.
- 목록 API에는 프로젝트 관례에 맞는 페이지네이션과 정렬을 사용한다.
- 재시도 가능한 작업은 멱등성을 검토한다.

## Compatibility

- 기존 필드 삭제, 이름·타입 변경, 의미 변경은 breaking change로 취급한다.
- 호환 가능한 확장인지 소비자에게 영향을 주는 변경인지 구분한다.
- 버전 추가는 실제 호환성 요구가 있을 때만 한다.
- 폐기 예정 기능에는 전환 경로와 기간을 문서화한다.

## Validation and Errors

- 경계에서 입력을 검증한다.
- 오류 응답은 일관된 코드, 사용자 안전 메시지, 추적 가능한 식별자를 사용한다.
- 4xx와 5xx를 원인에 맞게 구분한다.
- 내부 클래스명, 쿼리, 스택 추적, 민감 정보를 응답하지 않는다.

## Security

- 인증 여부와 별개로 해당 리소스에 대한 권한을 확인한다.
- 대량 할당, 객체 식별자 노출, 과도한 데이터 반환을 점검한다.
- 비밀값과 개인정보는 기본 응답에서 제외한다.
- 파일 업로드는 크기, 형식, 저장 위치, 악성 콘텐츠 위험을 검토한다.

## Documentation and Tests

새 엔드포인트 또는 계약 변경에는 다음을 제공한다.

- 요청·응답 예제
- 주요 상태 코드
- 인증·권한 요구
- 경계 및 오류 사례
- 관련 계약 또는 통합 테스트

문서 예제는 실행 가능한 실제 스키마와 일치시킨다.
