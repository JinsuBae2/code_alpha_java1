# AI Agent Rules

## Mission

사용자의 실제 요청을 정확하고 단순하며 유지보수 가능한 방식으로 해결한다.
코드를 많이 만드는 것이 아니라 필요한 결과를 검증 가능하게 만드는 것이 목표다.

## Instruction Order

- 현재 사용자의 명시적 요청을 가장 먼저 따른다.
- 저장소의 상위 및 하위 지침을 읽고 적용 범위를 확인한다.
- 프로젝트 사실은 `PROJECT_RULES.md`와 실제 코드·설정·문서를 통해 확인한다.
- 지침이 충돌하면 더 구체적이고 현재 작업에 가까운 지침을 우선하되 충돌을 알린다.

## Task-specific Rules

기본적으로 이 문서를 적용하고, 작업 성격에 따라 다음 문서를 추가로 읽는다.

- 구현·버그 수정·리팩터링: `CODING_RULES.md`, 완료 전 `CHECKLIST.md`
- Java/Spring 백엔드: `BACKEND_RULES.md`
- HTTP API 추가·변경: `API_RULES.md`
- 코드 리뷰: `REVIEW.md`
- 학습·멘토링: `LEARNING.md`
- 중요한 기술·보안·데이터·공개 계약 결정: `DECISION.md`
- 사용자 선호 또는 장기 기억을 기록·수정: `DEVELOPER.md`, `MEMORY.md`

`PROJECT_RULES.md`는 프로젝트별 사실을 기록한 문서다. 대괄호로 남은 템플릿
항목은 사실이나 규칙으로 간주하지 않고, 실제 코드·설정·문서에서 확인한다.

## Before Acting

1. 요청을 한 문장으로 정리한다.
2. 관련 파일, 테스트, 문서, 설정을 먼저 찾는다.
3. 기존 구조와 명명법, 구현 패턴을 파악한다.
4. 사실과 가정을 구분한다.
5. 수정 범위와 검증 방법을 정한다.

되돌리기 어렵거나 범위를 크게 바꾸는 선택만 사용자에게 확인한다. 안전하고
명확한 범위에서는 합리적인 가정으로 진행하되 결과에 가정을 적는다.

## Implementation

- 요청을 만족하는 가장 작은 변경을 한다.
- 기존 구현과 패턴을 새 코드보다 우선한다.
- 관련 없는 파일, 이름, 포맷, 패키지 구조를 바꾸지 않는다.
- 필요성이 증명되지 않은 추상화, 계층, 라이브러리, 설정 옵션을 추가하지 않는다.
- 존재 여부를 확인하지 않은 API, 클래스, 명령, 파일을 만들어 내지 않는다.
- 비밀값을 코드·로그·문서에 기록하지 않는다.
- 사용자의 기존 변경을 보존한다.

## Ambiguity

- 로컬 파일이나 문서로 확인 가능한 사항은 먼저 조사한다.
- 결과가 크게 달라지는 핵심 선택만 짧게 질문한다.
- 질문 없이 진행할 수 있다면 선택한 가정과 영향을 명시한다.
- 모르는 것을 아는 것처럼 표현하지 않는다.

## Verification

변경 위험에 비례해 다음을 확인한다.

- 포맷 또는 정적 검사
- 컴파일 또는 빌드
- 관련 자동화 테스트
- 핵심 사용자 흐름
- 호환성, 보안, 데이터 영향

실행하지 않은 검증을 통과했다고 말하지 않는다. 검증할 수 없었다면 이유와
사용자가 실행할 정확한 방법을 적는다.

## Communication

- 결과를 먼저 말하고 필요한 설명을 이어간다.
- 기본 언어는 한국어로 하되 코드 식별자와 공식 용어는 원문을 유지한다.
- 변경 파일, 변경 이유, 검증 결과, 남은 위험을 간결하게 보고한다.
- 작업 성격에 맞는 추가 규칙은 위의 `Task-specific Rules`를 따른다.

## Definition of Done

- 요청한 범위가 구현되었다.
- 관련 검증을 수행하고 결과를 확인했다.
- 기존 동작과 공개 계약에 대한 영향을 점검했다.
- 관련 없는 변경이 없다.
- 미확인 사항과 남은 위험을 숨기지 않았다.
