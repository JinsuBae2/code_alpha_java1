# General Coding Rules

## Existing Code First

- 새 코드를 쓰기 전에 같은 목적의 구현을 검색한다.
- 현재 저장소의 명명법, 파일 배치, 오류 처리, 테스트 스타일을 따른다.
- 공통화는 실제 중복과 안정된 패턴이 확인된 뒤 수행한다.

## Scope

- 요청을 해결하는 최소 범위만 수정한다.
- 관련 없는 리팩터링, 이름 변경, 포맷 변경, 의존성 갱신을 섞지 않는다.
- 공개 API, 저장 형식, 데이터베이스 스키마 변경은 명시적으로 다룬다.
- 생성 코드나 빌드 산출물을 직접 수정하지 않는다.

## Design

- 단순한 함수와 명확한 데이터 흐름을 선호한다.
- 하나의 함수·클래스가 지나치게 많은 책임을 맡으면 작업 범위 안에서만 분리한다.
- 추상화는 현재 필요한 변형과 사용 사례가 있을 때 도입한다.
- 오류를 숨기지 말고 호출자가 처리할 수 있는 형태로 전달한다.
- 경계에서 입력을 검증하고 내부 불변식을 명확히 유지한다.

## Readability

- 도메인 의미가 드러나는 이름을 사용한다.
- 주석은 코드가 무엇을 하는지보다 왜 그렇게 하는지 설명한다.
- 매직 넘버와 중복 문자열은 의미 있는 이름으로 관리하되 일회성 값까지 과도하게 추출하지 않는다.
- 함수의 부작용과 외부 의존성을 쉽게 파악할 수 있게 한다.

## Security and Privacy

- 비밀키, 토큰, 비밀번호, 개인정보를 코드·테스트·로그에 넣지 않는다.
- 외부 입력은 신뢰하지 않는다.
- 인증과 권한 검사를 혼동하지 않는다.
- 오류 응답과 로그에서 내부 구현 및 민감 정보를 노출하지 않는다.
- 새로운 의존성은 필요성, 유지 상태, 라이선스, 보안 영향을 확인한다.

## Tests

- 버그 수정에는 가능하면 실패를 재현하는 테스트를 먼저 추가한다.
- 기능 변경에는 정상 경로와 중요한 경계·오류 경로를 검사한다.
- 구현 세부보다 외부에서 관찰 가능한 동작을 테스트한다.
- 불안정한 시간, 네트워크, 무작위성은 제어한다.

## Comments and Documentation

- 공개 계약이나 운영 방법이 바뀌면 관련 문서를 함께 갱신한다.
- 코드와 어긋난 문서는 수정하거나 제거한다.
- 자동으로 알 수 있는 내용을 장황하게 반복하지 않는다.
